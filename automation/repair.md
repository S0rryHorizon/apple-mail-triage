# Independent mailbox repair

The user authorized automatic local repair as a fallback for returned operational failures. New chat-cleanup, content, validation and user-permission issues cannot automatically start a repair task; runtime launch gates enforce this. Cleanup recovery instructions below remain applicable to previously launched tasks or an explicit manual repair. Model/effort come from settings.json. Read runtime.py `repair.get` for the supplied incident_id and call `repair.attach` with this task's actual ID. If automation is paused, stop without restarting it or rescanning.

For an explicit user request to repair in the current chat, attach that chat with `manual: true, confirmed: true` after `repair.prepare`. It may recover the existing weekly task in place using `repair.retry` without a replacement. Manual repair chats are not automatically archived; the independent-task archive instructions below apply only to automatically created repair chats.

If an earlier repair ended failed before using its retry, explicit manual attachment may take over that incident directly. This requires an active schedule and a failed operational run; it preserves the previous repair chat ID and never resets the retry allowance. Paused, unknown, already retried, and resolved runs cannot be reopened this way.

Diagnose with current project source, the failed task's tool results when accessible, and synthetic tests. You may fix mailbox-project source/configuration, back up and reinstall its bridge/skill, and restart the affected workflow. Preserve unrelated working changes, mailbox state and project identity. Global Codex settings, account login, system permissions and permission prompts need the user's action; report these boundaries when they are the actual blocker.

Do not send or modify mail, loosen attachment protections, use raw mail in fixtures, or create another repair task. Iterate within this task as needed. Back up installed artifacts and use SQLite's backup API for MailTriage state before deployment; never read Apple's private Mail database. Validate only affected behavior.

## Recover once

- For `cleanup.archive`, repair the incident's `target_thread_id` on `target_host_id`, not its reporting `failed_thread_id`. Inspect that exact target. After an explicitly successful archive, call `cleanup.record` with `target_thread_id`. Mail/report completion alone cannot resolve an archive incident; `repair.finish` requires the target's recorded outcome as well. `repair.retry` returns `cleanup_only`: never replace or rescan the accepted weekly run for cleanup trouble.
- If the registered local target cannot be read, absence from a paginated list or an App error mentioning durable is insufficient. A bounded, read-only check may verify the exact ID is absent from both the local Codex task index and local active/archived session files. Only after both checks succeed, call `cleanup.record` with `outcome: "missing"`, `incident_id`, `target_thread_id`, and `verification: {"host_id":"local","index_absent":true,"rollout_absent":true}`. This retires only the obsolete cleanup reference; it does not archive/delete a chat and must be reported as such. Never write Codex's task database directly. Uncertain, inaccessible or still-existing targets remain unresolved and blocked, not missing. Retained weekly tasks and running tasks cannot be retired this way.
- An older cleanup incident without a target needs reconstruction from the failed archive call before recovery can be claimed. Do not guess from the reporting task. Keep an unknown outcome visible; it is not a retry trigger.
- Call `repair.get` again. If the run is already recorded, inspect its actual final report using `wait_threads`/a bounded task read; do not rescan. If the reply was interrupted after state saving, recover the prepared report from that task's existing context. If unavailable, report failure rather than fabricate completion.
- If a fork was registered but naming/delivery is still pending, finish setup on that known child instead of creating another fork.
- Otherwise use at most one `repair.retry`. If the weekly task itself failed, or there is no usable weekly task, fork the blank template identified by `repair.get.template_id`, following [task-creation.md](task-creation.md). Register the returned child with `repair.retry` and replacement_thread_id, rename it to the original run title, then deliver the returned prompt/model/thinking once. The template starts no scan itself. Retain the old task until success. If only the dispatcher failed and the weekly task remains usable, omit replacement_thread_id.
- `repair.retry` returns the exact thread_id/prompt/model/thinking for one `send_message_to_thread`. If a required App tool is absent, local CLI `queue` may deliver that exact prompt once only when no delivery was attempted; use subprocess argument arrays, including configured model/effort, and require exit 0. Never replay an unknown delivery.
- Observe completion with a bounded `wait_threads`, using its cursor when continuing. Check both runtime phase recorded and the actual final report/empty receipt. A queued prompt, successful build or saved state alone is insufficient.
- Call `repair.finish` with success:true and report_delivered:true only after both are confirmed and, for cleanup, the original target is recorded as archived or verified missing. Archive returned archive_ids serially, acknowledging each with `cleanup.record`. These are resolved reporting tasks, not proof that the original target was repaired. If this final archive itself fails, register that actual target with `cleanup.failed`, mark the returned incident failed with `repair.finish(success:false)`, and leave it visible without creating another repairer. Report what was repaired and where the recovered report lives.
- On failure, missing required user action, or a second triage failure, call `repair.finish` with success:false, leave broken tasks visible, and report the concrete blocker. An incident remains unresolved and cannot spawn another repairer automatically.
- On success, report the recovery result and report location, then make one final self-archive attempt. If the call returns and the turn continues, acknowledge it with `cleanup.record` using this repair task's `target_thread_id`. `repair.finish` also registers the successful repair task for the next dispatcher's cleanup, so self-archive ending the turn cannot strand it. Failed or incomplete repair tasks stay visible.

A repair task started through CLI persists as a normal independent Codex task. If its App tool catalog is absent, use available official CLI commands only where their result can establish the same outcome. Do not alter global plugins/settings or bypass unavailable permissions to manufacture success.
