# Returned failure handling

Automatic repair is a fallback for operational failures that block mailbox work. It does not apply to chat cleanup, individual unreadable content, attachment conversion/policy limits, invalid request fields, missing user details, permissions requiring user action, a fully hung/no-result call, or calendar writes. Report unknown outcomes without replaying them. Never resume a user-paused schedule.

Background MailBridge calls use `bridge.call`: it parses error JSON even on nonzero exit, preserves `errorCode`, closes the run and returns an already-registered `recovery` result. Reuse that result instead of calling `incident.open` again. Correct a rejected request in the existing task; report genuine user-action blockers there. Body/content limitations use the partial procedure. The runtime enforces exclusions in incident creation and every automatic launch path.

1. For archive failures, call runtime.py `cleanup.failed` with run_id, current `thread_id`, the actual failed `target_thread_id`, `target_host_id: "local"` and outcome `failed` or `unavailable`. Keep the reporting task and target distinct. The runtime records and deduplicates this cleanup issue, returns `repair: false`, and blocks automatic retries of that target. Stop cleanup without launching a repairer or treating mail triage as failed. If the dispatcher already recorded it, reuse the result. For operational failures not already registered by `bridge.call`, call `incident.open` with run_id when known, current thread_id, stage, the returned errorCode when available, and outcome `failed` or `unavailable`. Never save raw error output containing private content. If `repair: false`, stop automatic recovery; do not repeatedly alert on an unchanged issue.
2. Only for `repair: true`, call `repair.prepare` with the incident_id. When `launch: true`, use returned `task` with [task-creation.md](task-creation.md). When false, stop; no fallback is authorized. Both repair and triage inherit the blank template's mailbox permissions; do not use ordinary `create_thread` for the repairer.
3. Only if required App fork/archive tools are absent, or creation definitely failed before creating a task, call `repair.cli` with incident_id and reason `tool_unavailable` or `creation_definitely_failed`. It launches one local Codex CLI repair task with explicit full mailbox-workflow execution permissions and the configured repair model. The CLI is resolved from `CODEX_CLI_PATH` or PATH, so app bundle layout changes do not break it. Never use this fallback after an unknown creation result or a known child threadId. An explicit user denial of a creation or permission request stops that action; it is not authorization for a fallback.
4. Leave the failed task visible, state the incident and repair status, and stop this run. The repairer decides recovery success. If launch itself fails, report that failure; do not recursively launch repairers.

The helper allows one repair task per unresolved incident. Archive incidents are keyed by their actual target, not model-chosen error names; mail failures remain separate. Later encounters add affected reporting task IDs to the incident. Unresolved archive targets are excluded from automatic cleanup retries, but remain visible as blocked. A failed/ambiguous App lookup, including an unavailable durable host, is not proof that a local task was deleted. No timer, daemon or independent hang detector runs.
